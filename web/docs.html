How deployments work

Crelan accepts a deployment request, builds or pulls the application image, and rolls it out in your workspace. The workspace API is CI-provider neutral. GitHub Actions, GitLab CI, Jenkins, and other runners can all call the CLI or API.

Choose the path that fits your source: build an image in your CI pipeline for GitLab-hosted or other source repositories. Crelan-managed source builds currently accept GitHub repository URLs; private GitHub repositories need a connected GitHub App.

Quickstart

  1. Sign in to your Crelan workspace.
  2. Create a workspace API token with deployment write access (and read access if your pipeline waits for rollout status).
  3. Set CRELAN_API_URL and CRELAN_TOKEN in your runner's protected secret store or local shell.
  4. Deploy an existing container image or provide a GitHub repository for automated builds.
export CRELAN_API_URL="https://crelan.example.com"
export CRELAN_TOKEN="<workspace-token>"

# Existing image built and pushed by CI
crelan deploy --name storefront --image ghcr.io/acme/storefront:$GIT_COMMIT --wait

# Crelan clones and builds a GitHub repository
crelan deploy --name storefront \
  --repo https://github.com/acme/storefront --branch main --wait

The CLI reads the API URL and token from environment variables. Keep the token in CI's secret manager, not in source control or a build argument.

Workspace tokens for CI

Workspace tokens are scoped, revocable credentials for authenticating CI/CD pipelines, CLI commands, and automated deployments. The token secret is returned once upon creation; Crelan stores a secure hash and displays only its prefix afterward.

Generate a workspace token

You can generate workspace tokens directly in the dashboard UI or programmatically via the Crelan API:

Option A: Using the dashboard UI (Recommended)

  1. Sign in to your Crelan workspace and click the API Tokens tab in the sidebar.
  2. Enter a descriptive name for your token (e.g. github-actions-deployer or ci-pipeline).
  3. Select an expiration period: 7 days, 30 days, 90 days, 1 year (365 days), or No expiration.
  4. Select the required access scopes using the interactive checkboxes (see scopes table below).
  5. Click Generate API token.
  6. Click Copy token to clipboard and store the token immediately in your CI/CD secret manager (e.g., GitHub Secrets, GitLab CI/CD Variables). The full token value is shown only once and cannot be retrieved later.

Option B: Using the REST API

You can also create tokens via POST /api/v1/tokens using an authenticated session or another token with management permissions:

curl -X POST "$CRELAN_API_URL/api/v1/tokens" \
  -H "Cookie: crelan_session=<session-token>" \
  -H "Content-Type: application/json" \
  --data '{
    "name": "ci-deploy-token",
    "scopes": ["deployments:write", "deployments:read", "logs:read"],
    "expires_in_days": 90
  }'
Protect the token. Anyone holding it can act within its scopes until it expires or is revoked. Use a separate token per CI system, restrict it to protected branches/environments, and do not print it in job logs.

Scopes

ScopeGrants
deployments:writeCreate, cancel, delete, configure, or roll back deployments.
deployments:readList deployments and read status or deployment history.
logs:readRead application logs.
resources:readRead application and workspace resource metadata.
usage:readRead workspace usage and limits.
audit:readRead workspace audit events.

For a CI job that deploys and waits for completion, grant deployments:write and deployments:read. CLI log and resource commands also need their matching read scopes. Expiry can be set from 1 to 365 days. Revoke a token with DELETE /api/v1/tokens/{id}.

Add it to your CI provider

  • GitLab: add CRELAN_API_URL, CRELAN_TOKEN, and CRELAN_APP_NAME under Settings → CI/CD → Variables. Mark the token masked and protected.
  • Jenkins: save the API URL and token in Credentials, then expose them to the deploy stage with withCredentials.
  • GitHub Actions: store the token as a repository or environment secret and the API URL as a variable.

Build in CI and deploy an image

This is the portable option for GitLab, Jenkins, GitHub Actions, or any runner that can build and push an image. Images can be public or hosted on private registries by saving a registry credential in your Crelan workspace.

Pipeline steps

  1. Check out the application source code.
  2. Build an image and tag it with an immutable commit SHA or release tag.
  3. Push it to a container registry accessible to Crelan.
  4. Run crelan deploy --image and wait for the rollout.
docker build --pull -t "$IMAGE_TAG" .
docker push "$IMAGE_TAG"
crelan deploy --name "$CRELAN_APP_NAME" \
  --image "$IMAGE_TAG" \
  --image-pull-secret "$CRELAN_IMAGE_PULL_SECRET" \
  --port 8080 --wait

Omit --image-pull-secret for a public image. The workspace credential name is not the registry password; create the credential in Crelan and select its name when deploying.

GitLab CI

The repository includes a GitLab pipeline example at examples/ci/gitlab-ci.yml. It builds and pushes to the GitLab Container Registry, posts the image deployment to Crelan, and waits for the app to become running. Its Docker-in-Docker runner must allow privileged services.

Jenkins

The example examples/ci/Jenkinsfile builds and pushes the checked-out source. Configure credentials with IDs crelan-api-url, crelan-token, and container-registry, then set an app name and image repository. The Jenkins agent needs Docker, curl, and jq.

Any other CI

Install the Crelan CLI in the runner and use the same environment variables. The underlying API also works directly; see API reference.

Let Crelan build from source

Send Crelan an HTTPS GitHub repository URL and branch. Crelan automatically clones the repository and builds your application using the build mechanism you choose.

Build mechanisms

You can configure how your repository is built using the Build mechanism selector in the dashboard or via the CLI and API:

MechanismEngineDescription
auto (Default)Auto-detectChecks if the repository contains a Dockerfile. If present, it builds with BuildKit; otherwise, it builds using Cloud Native Buildpacks.
dockerfileRootless BuildKitBuilds the container image using an in-cluster BuildKit builder. You can specify a custom Dockerfile path (defaults to Dockerfile).
buildpackCloud Native Buildpacks (kpack)Automatically detects application dependencies (Node.js, Python, Go, Java, Ruby) and builds without needing any Dockerfile.

✨ Built-in Dockerfile Generator

Don't have a Dockerfile yet? Crelan includes an interactive Dockerfile Generator directly inside the deploy screen. Click ✨ Generate Dockerfile to view and customize optimized, multi-stage production Dockerfiles for your framework:

  • Node.js: Multi-stage build with Alpine runtime, npm ci --omit=dev dependency isolation, and non-root execution.
  • Python: Python 3.11 slim image with non-root appuser, virtual environment caching, and pip cleanup.
  • Go: Multi-stage compiler using golang:1.22-alpine, static linking (CGO_ENABLED=0), and minimal Alpine runtime.
  • Rust: Multi-stage cargo build --release with Debian bookworm slim runtime.
  • Java / Spring Boot: Maven package build with Eclipse Temurin 21 JRE Alpine runtime.
  • Static Web / SPA: Nginx Alpine with custom client-side SPA routing (try_files $uri /index.html).

Click Apply preset to configure your deploy form, or Copy to clipboard to save it directly into your Git repository.

# Build using repository Dockerfile
crelan deploy --name storefront \
  --repo https://github.com/acme/storefront \
  --branch main --dockerfile Dockerfile \
  --port 8080 --wait

# Build automatically using Buildpacks

Private GitHub repositories

For private GitHub repositories, Crelan offers two secure options:

  • GitHub App Integration (Recommended): Click Connect GitHub App in the dashboard or navigate to /settings/github/install. This grants read access to selected repositories and enables automatic zero-downtime rollouts on every git push via webhooks.
  • Personal Access Token: Enter a GitHub Personal Access Token (PAT with repo scope) directly into the Private repo token field during deployment.

GitHub Actions can also deploy the current repository with the official composite action at .github/actions/deploy; configure the API URL and workspace token in repository variables and secrets.

Private container registries

Crelan can pull application images from private registries including GitHub Container Registry (ghcr.io), Docker Hub (docker.io), GitLab Registry (registry.gitlab.com), AWS ECR, and self-hosted registries. Registry credentials are stored natively as Kubernetes kubernetes.io/dockerconfigjson Secrets (imagePullSecrets) inside your isolated tenant workspace namespace.

Add registry credentials

You can add credentials directly in the deployment modal by clicking ＋ Add registry credential, or via the API using your session:

curl -X POST "$CRELAN_API_URL/api/v1/registry-credentials" \
  -H "Cookie: crelan_session=<session-token>" \
  -H "Content-Type: application/json" \
  --data '{
    "name": "ghcr-production",
    "server": "ghcr.io",
    "username": "deploy-robot",
    "password": "<personal-access-token>"
  }'

Passwords and personal access tokens are stored securely in Kubernetes and are never returned in plaintext by the API. Once saved, select the credential name from the Private registry credential dropdown in the dashboard or pass it to the CLI:

crelan deploy --name api \
  --image ghcr.io/acme/api:1.4.2 \
  --image-pull-secret ghcr-production \
  --port 8080 --wait

To remove a registry credential, use DELETE /api/v1/registry-credentials/{name}.

Environment variables & secrets

Applications can be configured with runtime environment variables and sensitive encrypted secrets. When configuration is updated, Crelan triggers an immediate zero-downtime rolling update with the new settings.

Update configuration

curl -X PUT "$CRELAN_API_URL/api/v1/deployments/<id>/configuration" \
  -H "Authorization: Bearer $CRELAN_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{
    "environment": {
      "NODE_ENV": "production",
      "PORT": "8080"
    },
    "secrets": {
      "API_KEY": "sk_live_93817293812739",
      "SESSION_SECRET": "d38f82a93b4c102"
    }
  }'

Environment variable names must be alphanumeric and start with a letter (e.g. DATABASE_URL, APP_PORT). Secret values remain encrypted at rest and are injected directly into running containers without being returned in metadata.

Saved external connections

Save database or cache connection credentials once under Connections in the dashboard. You can attach saved connections directly to any deployment, mapping individual connection keys (like host, port, username, password) to environment variables.

Custom domains & SSL

Every application receives a default generated URL once running. You can attach your own custom domain (e.g. api.example.com or app.mycompany.org) with automatic TLS/SSL certificate generation and HTTPS routing.

Add and verify a custom domain

  1. Add the domain: Request domain attachment through the dashboard or API: 
    curl -X POST "$CRELAN_API_URL/api/v1/deployments/<id>/domains" \
  -H "Authorization: Bearer $CRELAN_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"host": "api.example.com"}'
    The response returns the custom domain ID, current status (pending), and a unique verification_token.
  2. Configure DNS records: Add the following records in your DNS provider:
    Record TypeHost / NameTarget / Value
    TXT_crelan-verify.api.example.com<verification_token>
    CNAMEapi.example.com<your-app-default-domain>
  3. Verify domain ownership: Trigger verification once your DNS records propagate: 
    curl -X POST "$CRELAN_API_URL/api/v1/deployments/<id>/domains/<domain_id>/verify" \
  -H "Authorization: Bearer $CRELAN_TOKEN"
    When verification succeeds, the domain status changes to active, and HTTPS traffic routes directly to your application.

List configured domains with GET /api/v1/deployments/{id}/domains and remove domains with DELETE /api/v1/deployments/{id}/domains/{domain_id}.

Rollbacks & deployment history

Crelan maintains a comprehensive history of all deployment runs for each application. If a new deployment introduces a regression, you can roll back immediately to any previous successful rollout.

Dashboard UI: One-click rollback

Open the application details view in the Crelan dashboard. The Deployment history panel lists all previous builds, commit SHAs, image digests, timestamps, and deployment status. Click the Rollback button next to any successful deployment run to trigger an immediate, zero-downtime rolling update restoring that exact configuration.

Live Pod warning events

If an application fails to start or gets stuck in CrashLoopBackOff or ImagePullBackOff, the dashboard inspects the Kubernetes cluster events in real time and highlights warning events directly in the application header and logs panel (accessible via API at GET /api/v1/deployments/{id}/events).

View deployment runs via CLI or API

crelan history <id>
# Or via API
curl -H "Authorization: Bearer $CRELAN_TOKEN" \
  "$CRELAN_API_URL/api/v1/deployments/<id>/history"

Trigger an instant rollback via API

Pass the target run_id of a previous successful run. Crelan will immediately roll back your app to that exact image/source configuration:

curl -X POST "$CRELAN_API_URL/api/v1/deployments/<id>/rollback" \
  -H "Authorization: Bearer $CRELAN_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"run_id": 14}'

Cancel an in-progress deployment

To cancel a deployment that is currently queued or building, send a cancel request:

curl -X POST "$CRELAN_API_URL/api/v1/deployments/<id>/cancel" \
  -H "Authorization: Bearer $CRELAN_TOKEN"

Persistent storage & retained volumes

For applications that require persistent file storage (e.g. SQLite databases, CMS uploads, cache directories), attach dedicated persistent disk storage to your deployment.

crelan deploy --name cms \
  --image ghost:5-alpine \
  --port 2368 \
  --storage-gib 10 \
  --storage-mount-path /var/lib/ghost/content \
  --wait

Volume retention guarantee

To protect against accidental data loss, persistent storage volumes are retained when an application is redeployed or deleted. Retained volumes can be inspected under Storage → Retained app volumes in the dashboard or via API:

curl -H "Authorization: Bearer $CRELAN_TOKEN" \
  "$CRELAN_API_URL/api/v1/workspace/storage"

To permanently delete a retained volume and free disk quota after an application has been decommissioned:

curl -X DELETE -H "Authorization: Bearer $CRELAN_TOKEN" \
  "$CRELAN_API_URL/api/v1/workspace/storage/cms"

Dedicated VM servers (AWS EC2)

In addition to managed container workloads, Crelan can provision and manage dedicated virtual machines directly inside your own AWS account or managed infrastructure. This enables running containerized services with full VM isolation, custom system tuning, and dedicated hardware resources.

Connect your AWS account

Crelan connects securely via cross-account IAM role assumption—never requiring long-lived AWS root or IAM user access keys. Retrieve your workspace's external ID connection parameters via GET /api/v1/aws/connection and create the requested IAM role in your AWS account.

Provision a server

curl -X POST "$CRELAN_API_URL/api/v1/servers" \
  -H "Cookie: crelan_session=<session-token>" \
  -H "Content-Type: application/json" \
  --data '{
    "name": "worker-1",
    "mode": "customer_aws",
    "region": "us-east-1",
    "instance_type": "t3.small",
    "role_arn": "arn:aws:iam::123456789012:role/CrelanDeployRole",
    "external_id": "<workspace-external-id>",
    "ssh_source_cidr": "203.0.113.0/24"
  }'

Crelan provisions an Amazon Linux 2023 instance, installs Docker and the lightweight crelan-agent, and returns an Ed25519 SSH private key once for download.

Deploy containers to VM servers

Deploy applications directly to any active server:

curl -X POST "$CRELAN_API_URL/api/v1/servers/<server_id>/deployments" \
  -H "Cookie: crelan_session=<session-token>" \
  -H "Content-Type: application/json" \
  --data '{"image": "redis:7-alpine", "port": 6379}'

Use POST /api/v1/servers/{id}/stop and POST /api/v1/servers/{id}/start to control instance lifecycle and save cloud costs when servers are idle.

curl -X POST "$CRELAN_API_URL/api/v1/databases" \

Private DNS service discovery

Databases are isolated within your workspace network and do not expose public ports. Applications in the same workspace connect securely using internal hostnames (for example, production-db or production-db-rw for write replicas). Database credentials are shown once at creation time and can be mapped into application environment variables.

Database backups & restore

Production databases include automated daily snapshots stored in durable, encrypted object storage. You can also trigger manual snapshots before major schema migrations or application upgrades.

Create an on-demand snapshot

curl -X POST "$CRELAN_API_URL/api/v1/databases/production-db/backups" \
  -H "Cookie: crelan_session=<session-token>"

List completed backups

curl "$CRELAN_API_URL/api/v1/databases/production-db/backups" \
  -H "Cookie: crelan_session=<session-token>"

Restore from backup

To restore data from the latest completed backup snapshot into a fresh database instance:

curl -X POST "$CRELAN_API_URL/api/v1/databases/production-db/restore" \
  -H "Cookie: crelan_session=<session-token>"

GitHub Actions

Automate continuous deployment directly from your GitHub repository using the official composite action at .github/actions/deploy. Every push to your default branch automatically builds and rolls out your changes.

name: Deploy to Crelan

on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Deploy application
        uses: ./.github/actions/deploy
        with:
          api-url: ${{ vars.CRELAN_API_URL }}
          token: ${{ secrets.CRELAN_TOKEN }}
          app-name: storefront
          branch: main
          port: "8080"
          cpu-millicores: "1000"
          memory-mib: "512"

Store CRELAN_TOKEN in GitHub Repository Secrets and CRELAN_API_URL in Repository Variables.

GitLab CI

Set CRELAN_API_URL, CRELAN_TOKEN, and CRELAN_APP_NAME as CI/CD variables. Mask and protect the token. The supplied example uses GitLab's registry and builds the current project before deployment.

deploy:image:
  stage: deploy
  script:
    - crelan deploy --name "$CRELAN_APP_NAME" \
        --image "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" --wait

If you want Crelan to build the source, use the manual deploy:source job in examples/ci/gitlab-ci.yml and set CRELAN_SOURCE_REPOSITORY to a GitHub URL. That source job cannot build the GitLab project itself yet.

Jenkins

Store the API URL and token in Jenkins Credentials. Build and push the app image in your pipeline, then deploy it with the CLI:

withCredentials([
  string(credentialsId: 'crelan-api-url', variable: 'CRELAN_API_URL'),
  string(credentialsId: 'crelan-token', variable: 'CRELAN_TOKEN')
]) {
  sh 'crelan deploy --name "$CRELAN_APP_NAME" --image "$IMAGE_NAME" --wait'
}

The supplied examples/ci/Jenkinsfile includes both image deployment and an optional Crelan-managed build from a public GitHub repo.

Terraform, OpenTofu, and Pulumi

Manage a Crelan deployment as an infrastructure resource. The integrations use the same workspace API and token scopes as the CLI. Build and push images in your normal pipeline, or use a supported GitHub repository as the source.

Terraform and OpenTofu

The Go provider exposes a crelan_deployment resource. It supports image and GitHub source deployments, waits for the deployment to become running, reads drift from the API, and deletes the Crelan app when the resource is destroyed.

export CRELAN_API_URL="https://crelan.example.com"
export CRELAN_TOKEN="<workspace-token>"
cd integrations/terraform-provider-crelan
go build -o terraform-provider-crelan .

Build the provider and install it into a local filesystem mirror as described in the integration README until it is published to a registry. The example configurations are in integrations/terraform-provider-crelan/examples/image and examples/source. OpenTofu uses the same provider protocol and configuration.

resource "crelan_deployment" "app" {
  name           = "storefront"
  image          = "ghcr.io/acme/storefront:1.4.2"
  port           = 8080
  wait_for_ready = true
}

output "url" {
  value = crelan_deployment.app.url
}

Pulumi TypeScript

The starter at integrations/pulumi provides a dynamic Deployment resource and uses Pulumi secret configuration for the workspace token.

cd integrations/pulumi
npm install
pulumi stack init dev
pulumi config set crelan:apiUrl https://crelan.example.com
pulumi config set --secret crelan:token '<workspace-token>'
pulumi config set crelan:appName storefront
pulumi config set crelan:image ghcr.io/acme/storefront:1.4.2
pulumi up
Provider availability: the Terraform/OpenTofu provider is source-only until a release is published to a provider registry. The Pulumi dynamic provider currently supports this TypeScript example only; dynamic providers do not support import or refresh reconciliation. See integrations/pulumi/README.md before using it with a production state backend.

Terraform/OpenTofu require deployments:write and deployments:read because Terraform reads the deployment during refresh and when waiting for readiness. The Pulumi example uses both scopes by default because it waits for readiness.

Teams & workspaces

Crelan workspaces provide isolated environments for your applications, databases, and secrets. You can invite team members to collaborate and switch seamlessly between multiple workspaces.

Member roles

RolePermissions
ownerFull access to workspace settings, billing, team member management, and resource deletion.
developerDeploy applications, configure environment variables/secrets, and provision databases.
viewerRead-only access to deployment status, metrics, logs, and workspace resources.

Invite a team member

Workspace owners can generate a secure one-time invite token from the Team tab or via the API:

curl -X POST "$CRELAN_API_URL/api/v1/workspace/invites" \
  -H "Cookie: crelan_session=<session-token>" \
  -H "Content-Type: application/json" \
  --data '{"role": "developer"}'

Share the returned one-time invite token with your collaborator. The recipient signs in and accepts the invite to join the workspace:

curl -X POST "$CRELAN_API_URL/api/v1/workspace/invites/accept" \
  -H "Cookie: crelan_session=<session-token>" \
  -H "Content-Type: application/json" \
  --data '{"token": "<invite-token>"}'

Switch between workspaces

List workspaces you belong to with GET /api/v1/workspaces, and switch active workspace with POST /api/v1/workspaces/switch passing {"workspace_id": <id>}.

Workspace quotas & audit logs

  • Limits: Inspect your workspace compute quotas and concurrent deployment limits with GET /api/v1/workspace/limits.
  • Audit trail: Review sensitive operational events (such as configuration changes, secret updates, and member management) with GET /api/v1/audit.
  • Usage: Monitor resource consumption history with GET /api/v1/usage.

Interactive Terminal UI (TUI)

Run crelan tui for a terminal dashboard. It provides an interactive interface to view running applications, monitor rollout status, stream application logs, deploy new images or repositories, and manage workloads without memorizing command-line flags.

Common deploy flags

  • --branch: Target Git branch for source builds (default: main).
  • --dockerfile: Path to Dockerfile in repository (default: Dockerfile).
  • --port: Application HTTP port (default: 8080).
  • --cpu-millicores: CPU allocation in millicores (default: 1000m).
  • --memory-mib: Memory allocation in MiB (default: 512Mi).
  • --storage-gib: Dedicated persistent storage volume size in GiB.
  • --storage-mount-path: Container filesystem path for storage volume mount (e.g. /data).
  • --image-pull-secret: Name of a saved workspace registry credential for private images.
  • --wait: Block CLI until deployment finishes rollout and reaches running or terminal state.
  • --wait-timeout: Maximum time to wait for deployment rollout (e.g. 10m, 30m).

Troubleshooting

503 Service Unavailable / Cluster Not Connected

If app deployments return 503 Service Unavailable with "no Kubernetes deployment provisioner configured", Crelan is not currently connected to an active Kubernetes cluster. This can happen if the control plane was restarted or redeployed on an ephemeral container host without persistent disk storage.

To persist cluster connectivity automatically across all future restarts and redeployments:

  • Set the environment variable (Recommended): Encode your kubeconfig YAML in base64 (base64 -w0 kubeconfig.yaml) and set it as the CRELAN_KUBECONFIG_DATA_B64 environment variable in your hosting platform (e.g., PipeOps Project Environment Variables). Crelan will automatically detect and connect to your cluster on every boot!
  • Connect via the Admin Dashboard: Sign in as a platform administrator, navigate to /assets/admin.html, paste your kubeconfig YAML into the connection form, and click Connect cluster.

401 or 403 from the API

Confirm that your workspace API token is active and includes the required scopes for the endpoint (e.g. deployments:write). Ensure you are calling the base URL without a trailing /api/v1 in the base path.

Custom domain verification pending or failed

Verify that your DNS TXT record is configured exactly at _crelan-verify.<your-domain> with the token value provided when the domain was created. DNS propagation can take a few minutes depending on your DNS provider's TTL.

ImagePullBackOff on deployment

Verify that the container image name and tag exist in the registry. For private repositories on GitHub Packages, Docker Hub, GitLab, or AWS ECR, make sure you have added a matching registry credential in your Crelan workspace and passed its name as --image-pull-secret.

Deployment stays queued or building

Check your workspace limits (GET /api/v1/workspace/limits) to confirm your workspace has not reached its maximum concurrent build quota. For source builds, ensure your GitHub repository URL and branch are accessible and that your repository contains a valid Dockerfile or matches supported Buildpack runtimes.

Application is running but no public URL

Ensure your application has an exposed port configured (defaults to 8080). If your app is active but has no public domain assigned, check that your service is listening on the configured HTTP port, or verify custom domain routing under the Domains tab.

Database connectivity issues

Databases are secured inside your workspace's private network. Ensure your application connects using the internal database hostname (e.g. orders-db) rather than trying to route over the public internet.

Revoke a leaked or retired token

Revoke the token immediately using your signed-in workspace session in the API Tokens tab or via the API (DELETE /api/v1/tokens/{id}), then generate a replacement with the minimum required scopes and update your CI secret manager.
