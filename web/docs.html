How deployments work

Crelan accepts a deployment request, builds or pulls the application image, and rolls it out in your workspace. The workspace API is CI-provider neutral. GitHub Actions, GitLab CI, Jenkins, and other runners can all call the CLI or API.

Choose the path that fits your source: build an image in your CI pipeline for GitLab-hosted or other source repositories. Crelan-managed source builds currently accept GitHub repository URLs; private GitHub repositories need a connected GitHub App.

Quickstart

  1. Sign in to your Crelan workspace and make sure an administrator has configured a Kubernetes cluster.
  2. Create a workspace API token with deployment write access. Add deployment read access if your pipeline waits for rollout status.
  3. Set CRELAN_API_URL and CRELAN_TOKEN in your runner's protected secret store.
  4. Deploy an image your cluster can pull, or choose a GitHub repo for Crelan-managed builds.
export CRELAN_API_URL="https://crelan.example.com"
export CRELAN_TOKEN="<workspace-token>"

# Existing image built and pushed by CI
crelan deploy --name storefront --image ghcr.io/acme/storefront:$GIT_COMMIT --wait

# Crelan clones and builds a GitHub repository
crelan deploy --name storefront \
  --repo https://github.com/acme/storefront --branch main --wait

The CLI reads the API URL and token from environment variables. Keep the token in CI's secret manager, not in source control or a build argument.

Workspace tokens for CI

Workspace tokens are scoped, revocable credentials. The token secret is returned only when created; Crelan stores a hash and shows only its prefix afterward. Token creation and revocation use your signed-in browser session. A token management form is not available in the dashboard yet, so use the signed-in browser console request below to create one.

Create a deployment token

  1. Sign in to Crelan in the browser that has access to the target workspace.
  2. Open the browser developer console while on your Crelan site.
  3. Run the request below, changing the name and expiry as needed. The example expires in 90 days.
  4. Copy the returned token value immediately into your CI secret store. The full value cannot be retrieved later.
const response = await fetch("/api/v1/tokens", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    name: "GitLab production deploy",
    scopes: ["deployments:write", "deployments:read"],
    expires_in_days: 90
  })
});
const result = await response.json();
if (!response.ok) throw new Error(result.error || "Token creation failed");
console.log(result.token);
Protect the token. Anyone holding it can act within its scopes until it expires or is revoked. Use a separate token per CI system, restrict it to protected branches/environments, and do not print it in job logs.

Scopes

ScopeGrants
deployments:writeCreate, cancel, delete, configure, or roll back deployments.
deployments:readList deployments and read status or deployment history.
logs:readRead application logs.
resources:readRead application and workspace resource metadata.
usage:readRead workspace usage and limits.
audit:readRead workspace audit events.

For a CI job that deploys and waits for completion, grant deployments:write and deployments:read. CLI log and resource commands also need their matching read scopes. Expiry can be set from 1 to 365 days. Revoke a token with DELETE /api/v1/tokens/{id}.

Add it to your CI provider

  • GitLab: add CRELAN_API_URL, CRELAN_TOKEN, and CRELAN_APP_NAME under Settings → CI/CD → Variables. Mark the token masked and protected.
  • Jenkins: save the API URL and token in Credentials, then expose them to the deploy stage with withCredentials.
  • GitHub Actions: store the token as a repository or environment secret and the API URL as a variable.

Build in CI and deploy an image

This is the portable option for GitLab, Jenkins, or any runner that can build and push an image. The image must be available to the Kubernetes cluster. For a private registry, first save a registry credential in the Crelan workspace.

Pipeline steps

  1. Check out the application source.
  2. Build an image and tag it with an immutable commit SHA or release version.
  3. Push it to a registry your cluster can reach.
  4. Run crelan deploy --image and wait for the rollout.
docker build --pull -t "$IMAGE_TAG" .
docker push "$IMAGE_TAG"
crelan deploy --name "$CRELAN_APP_NAME" \
  --image "$IMAGE_TAG" \
  --image-pull-secret "$CRELAN_IMAGE_PULL_SECRET" \
  --port 8080 --wait

Omit --image-pull-secret for a public image. The workspace credential name is not the registry password; create the credential in Crelan and select its name when deploying.

GitLab CI

The repository includes a GitLab pipeline example at examples/ci/gitlab-ci.yml. It builds and pushes to the GitLab Container Registry, posts the image deployment to Crelan, and waits for the app to become running. Its Docker-in-Docker runner must allow privileged services.

Jenkins

The example examples/ci/Jenkinsfile builds and pushes the checked-out source. Configure credentials with IDs crelan-api-url, crelan-token, and container-registry, then set an app name and image repository. The Jenkins agent needs Docker, curl, and jq.

Any other CI

Install the Crelan CLI in the runner and use the same environment variables. The underlying API also works directly; see API reference.

Let Crelan build from source

Send Crelan an HTTPS GitHub repository URL and branch. Crelan clones the source and builds a Dockerfile with rootless BuildKit. If there is no Dockerfile, Crelan can use the platform's configured Buildpacks builder.

crelan deploy --name storefront \
  --repo https://github.com/acme/storefront \
  --branch main --dockerfile Dockerfile \
  --port 8080 --wait

Public GitHub repositories can be built directly. Private GitHub repositories require the workspace's connected GitHub App. Crelan-managed source builds do not currently accept GitLab, Bitbucket, or arbitrary Git server URLs. For those repositories, let CI build and push the image, then use --image.

GitHub Actions can also deploy the current repository with the composite action at .github/actions/deploy; configure the API URL and workspace token in repository variables and secrets.

GitLab CI

Set CRELAN_API_URL, CRELAN_TOKEN, and CRELAN_APP_NAME as CI/CD variables. Mask and protect the token. The supplied example uses GitLab's registry and builds the current project before deployment.

deploy:image:
  stage: deploy
  script:
    - crelan deploy --name "$CRELAN_APP_NAME" \
        --image "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" --wait

If you want Crelan to build the source, use the manual deploy:source job in examples/ci/gitlab-ci.yml and set CRELAN_SOURCE_REPOSITORY to a GitHub URL. That source job cannot build the GitLab project itself yet.

Jenkins

Store the API URL and token in Jenkins Credentials. Build and push the app image in your pipeline, then deploy it with the CLI:

withCredentials([
  string(credentialsId: 'crelan-api-url', variable: 'CRELAN_API_URL'),
  string(credentialsId: 'crelan-token', variable: 'CRELAN_TOKEN')
]) {
  sh 'crelan deploy --name "$CRELAN_APP_NAME" --image "$IMAGE_NAME" --wait'
}

The supplied examples/ci/Jenkinsfile includes both image deployment and an optional Crelan-managed build from a public GitHub repo.

Terraform, OpenTofu, and Pulumi

Manage a Crelan deployment as an infrastructure resource. The integrations use the same workspace API and token scopes as the CLI. Build and push images in your normal pipeline, or use a supported GitHub repository as the source.

Terraform and OpenTofu

The Go provider exposes a crelan_deployment resource. It supports image and GitHub source deployments, waits for the deployment to become running, reads drift from the API, and deletes the Crelan app when the resource is destroyed.

export CRELAN_API_URL="https://crelan.example.com"
export CRELAN_TOKEN="<workspace-token>"
cd integrations/terraform-provider-crelan
go build -o terraform-provider-crelan .

Build the provider and install it into a local filesystem mirror as described in the integration README until it is published to a registry. The example configurations are in integrations/terraform-provider-crelan/examples/image and examples/source. OpenTofu uses the same provider protocol and configuration.

resource "crelan_deployment" "app" {
  name           = "storefront"
  image          = "ghcr.io/acme/storefront:1.4.2"
  port           = 8080
  wait_for_ready = true
}

output "url" {
  value = crelan_deployment.app.url
}

Pulumi TypeScript

The starter at integrations/pulumi provides a dynamic Deployment resource and uses Pulumi secret configuration for the workspace token.

cd integrations/pulumi
npm install
pulumi stack init dev
pulumi config set crelan:apiUrl https://crelan.example.com
pulumi config set --secret crelan:token '<workspace-token>'
pulumi config set crelan:appName storefront
pulumi config set crelan:image ghcr.io/acme/storefront:1.4.2
pulumi up

Terraform/OpenTofu require deployments:write and deployments:read because Terraform reads the deployment during refresh and when waiting for readiness. The Pulumi example uses both scopes by default because it waits for readiness.

CLI reference

Build the CLI from a Crelan source checkout with go build -o crelan ./cmd/crelan. Set CRELAN_API_URL to the base URL of your Crelan instance and CRELAN_TOKEN to a workspace token. Do not include /api/v1 in the base URL.

CommandPurposeRequired scope
crelan deploy --name APP --image IMAGEDeploy an existing image.deployments:write
crelan deploy --name APP --repo URLAsk Crelan to build a GitHub repository.deployments:write
crelan deploymentsList workspace deployments.deployments:read
crelan status IDRead current deployment status.deployments:read
crelan history IDRead prior deployment runs.deployments:read
crelan logs IDRead app logs.logs:read
crelan resources IDRead app pod/config metadata.resources:read
crelan delete IDDelete an application.deployments:write
crelan versionPrint the CLI version.None

For an interactive terminal menu, run crelan tui. It can list deployments, deploy an image or GitHub repository, inspect status/logs/resources, and delete an app after confirmation. It uses the same CRELAN_API_URL and CRELAN_TOKEN environment variables and is intended for an interactive terminal, not a CI script.

Useful deploy options include --branch, --dockerfile, --port, --cpu-millicores, --memory-mib, --image-pull-secret, --wait, and --wait-timeout. Deployment defaults are 8080 port, 1000m CPU, and 512 MiB memory, subject to workspace limits.

API reference

Send workspace-token requests with Authorization: Bearer $CRELAN_TOKEN and JSON content type. Deployment API routes are prefixed with /api/v1. Requests are scoped to the token's workspace.

GET /api/v1/deploymentsList workspace deployments.deployments:read

GET /api/v1/deployments/{id}/historyRead deployment run history.deployments:read
GET /api/v1/deployments/{id}/resourcesRead app resource metadata.resources:read
GET /api/v1/deployments/{id}/logsRead app logs; optional ?tail=200 (max 1000).logs:read

Create deployment request

curl --fail-with-body -X POST "$CRELAN_API_URL/api/v1/deployments" \
  -H "Authorization: Bearer $CRELAN_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"name":"storefront","image":"ghcr.io/acme/storefront:1.4.2","port":8080}'

For a source build, send repository_url, optional branch, and optional dockerfile instead of image. For an image, optional image_pull_secret selects a saved workspace registry credential. The response is asynchronous; poll the returned deployment ID until status is running or a terminal state.

Deployment statuses include queued, building, deploying, running, degraded, failed, deleting, deleted, and cancelled. Errors return a JSON error message and an HTTP error status.

Manage workspace tokens from your signed-in account. Use a separate token for each automation workflow and grant only the access it needs.

Troubleshooting

401 or 403 from the API

Confirm that the token is active, belongs to the intended workspace, and includes the required scope. Use the Crelan base URL without a trailing /api/v1.

ImagePullBackOff

Check the image name and tag, confirm the image is pushed before deployment, and select the saved registry credential for private images. Make sure cluster nodes can reach the registry.

Deployment stays queued or building

Check workspace concurrency limits, cluster capacity, and the Crelan deployment history/logs. Source builds need a supported GitHub URL and a configured builder and registry.

No public application URL

The cluster needs an ingress controller and platform-configured application domain. Contact your platform administrator if the app is running but has no URL.

Revoke a leaked or retired token

Use the signed-in token management endpoint to revoke it, then issue a replacement with the minimum required scopes and update your CI secret.
